# Security Fix 1: OpenJDK Base64 Intrinsic Heap Out-of-Bounds Write ("Java4Shell")

## Issue

TSI-Compass-Bundled-OpenJDK-Base64-Intrinsic-Heap-OOB-Write

**Class:** Out-of-bounds Write (CWE-787)

## CVE

**CVE-2026-114938**, publicly disclosed 2026-11-17 and widely reported under
the name "Java4Shell". This is a vulnerability in the OpenJDK runtime itself
(reported affected ranges: JDK 17.0.6-17.0.21, 21.x up to 21.0.13, 25.x up to
25.0.5), not in this application's own code.

## Reported By

Public disclosure by multiple independent security researchers/vendors
(including Datadog Security Labs, Talos Intelligence and watchTowr) from
2026-11-17. Not specific to this application; flagged here because the
project's Docker base image (`jetty:11-jdk17`) bundles an affected JDK build.

## Description

OpenJDK's C2 JIT compiler includes a hardware-accelerated ("intrinsic")
implementation of `java.util.Base64` decoding that, on CPUs supporting
AVX-512 VBMI, can write past the end of the destination buffer on certain
inputs - a heap out-of-bounds write reachable pre-authentication by any code
path that decodes attacker-supplied Base64 data (for example, Basic Auth
headers, JWTs, or any multipart/base64 upload handling). Public reporting
rates it up to CVSS 4.0 9.2 / CVSS 3.1 8.1; exact severity and official
upstream patch status were still unsettled across vendors as of 2026-11-18,
the day this fix was written - some sources claimed a fixed Oracle build,
others reported no published patch or technical root-cause confirmation yet.

Confirmed against this project's base image:
`docker run --rm jetty:11-jdk17 java -version` resolves to **Temurin
17.0.17** - inside the publicly reported affected range. Whether the
vulnerable intrinsic is actually selected at runtime depends on the
deployment host's CPU (AVX-512 VBMI support); hosts without it are not
exposed regardless, but this cannot be guaranteed across all deployment
environments, and the host used to build or run the image is not necessarily
the host serving production traffic. (On the host used to verify this fix,
`UseBASE64Intrinsics` already defaulted to `false`, consistent with that host
lacking AVX-512 VBMI - the mitigation below forces it off unconditionally so
a production host that *does* have AVX-512 VBMI isn't exposed either.)

## Our Fix

Added `ENV JAVA_TOOL_OPTIONS="-XX:-UseBASE64Intrinsics"` to the `Dockerfile`.
This forces the JVM to always use the plain-Java Base64 implementation
instead of the native intrinsic, regardless of what the host CPU supports -
removing the vulnerable code path entirely rather than relying on the
deployment host not having AVX-512 VBMI.

This is a **runtime mitigation, not an upstream patch**. It was applied
because, at time of writing, there was no cross-vendor consensus that
Oracle/OpenJDK had shipped a fixed JDK 17 build, and `jetty:11-jdk17` is a
floating tag outside this project's control, so the JDK version it resolves
to can change without notice. It should be revisited - and removed, or kept
as defense-in-depth - once the base image can be upgraded past the affected
JDK range.

Binary (non-Docker) installs are not covered by the `Dockerfile` change and
must set the same flag themselves, e.g. via
`JAVA_TOOL_OPTIONS=-XX:-UseBASE64Intrinsics` in the environment before
starting Jetty/the WAR. See the Changelog entry in [README.md](../../README.md).

**Verified:**
- `docker run --rm jetty:11-jdk17 java -version` confirms the bundled JVM is
  Temurin 17.0.17, within the affected range.
- `docker run --rm jetty:11-jdk17 java -XX:+PrintFlagsFinal -version` confirms
  `UseBASE64Intrinsics` is a valid, settable `product` flag on the bundled
  JVM (no `-XX:+UnlockDiagnosticVMOptions` required).
- `docker run --rm -e JAVA_TOOL_OPTIONS='-XX:-UseBASE64Intrinsics'
  jetty:11-jdk17 java -version` starts cleanly with the flag applied
  (confirmed via the `Picked up JAVA_TOOL_OPTIONS: ...` notice on stderr).

**Not verified:** no working exploit for CVE-2026-114938 was available at
time of writing, so this fix was not verified against a live reproduction.
It rests on the documented effect of the flag (disabling the intrinsic that
public reporting identifies as the vulnerable code path), not on a tested
before/after exploit comparison.
